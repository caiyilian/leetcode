## 是否最优解？✅ 是（get/put 均 O(1)，空间 O(capacity)）

| 考察点 | 结论 |
|--------|------|
| get 时间复杂度 | ✅ O(1)——hash_map 定位 O(1) + 链表移到最前 O(1)（4 次指针操作） |
| put 时间复杂度 | ✅ O(1)——命中更新 O(1)；未命中断言 + 驱逐 O(1) |
| 空间复杂度 | ✅ O(capacity)——hash_map（含反向映射）+ 链表各存 capacity 个节点，**不是"多"**，是标准实现该有的量级（力扣内存 29.1MB 与官方典型实现一致） |
| 正确性 | ✅ 官方示例 + 50 轮 × 2000 随机操作（10 万次，含驱逐/覆盖/get 刷新）vs OrderedDict 参照版 0 不一致 |

**用户疑问解答："空间占用有点多"**：29.1MB 对 LRU 是正常的——**哈希表 + 双向链表本来就各存一份节点引用**（键表 + 值链表 + 反向映射表），这是 O(1) 的代价。题目只要求 get/put O(1)，你的实现**完全满足**，空间是 O(capacity) 最优量级，无需担心。

## RE → AC 复盘（本次核心教训）

**RE 版**（19:46）驱逐时：

```python
self.hash_map.pop(delete_node.val)
# ❌ 用的是节点的 val 当 key 删——但 hash_map 的键是"用户 key"，不是节点值！
```

**场景**：`put(1,1)`（node.val=1）后容量满，若再 put 新键驱逐的是别的节点还好……但一旦被驱逐节点的 `val` 与某个其他 key 相同，就删错/删不到。RE 说明测试命中：**节点的 val 压根不等于它的 key**（比如 `put(1, 99)`，key=1 但 val=99）。

**修复（v2）**：加反向映射 `hash_map2[node] = key`，驱逐时：

```python
self.hash_map.pop(self.hash_map2[delete_node])   # 用反向映射拿到真 key
```

**教训**：**双向链表的节点存的是 value，不是 key**——LRU 驱逐要从链表尾删除节点，但 hash_map 要用 key 删，**必须知道"这个节点对应的 key 是谁"**。两种解法：
- 反向映射表（你的方案，O(1) 空间换 O(1) 时间）；
- 节点里直接存 key（ListNode 加 `self.key` 字段，官方常见写法，省一张表）。

# 128. 最长连续序列 · 解题解析

> 用户独立完成：首版为排序解法（O(n log n)），经提示后自行推导出 O(n) 解法，
> 并自主设计了两组对照实验，发现并修复了两个复杂度陷阱。

## 一句话思路

把数组放进**哈希集合**（O(1) 存在性查询），然后只从**连续段的起点**（`x - 1` 不在集合里）开始向后计数。
每一段只有唯一的一个起点，因此每个元素最多被计数一次 → **O(n)**。

## 最终实现

```python
class Solution:
    def longestConsecutive(self, nums: List[int]) -> int:
        if len(nums) == 0:
            return 0
        num_set = set(nums)
        max_length = 1
        for n in num_set:
            if n - 1 in num_set:      # 不是起点，跳过
                continue
            count = 1
            while True:               # 是起点，一路往后数
                if n + count in num_set:
                    count += 1
                else:
                    break
            max_length = max(max_length, count)
        return max_length
```

## 复杂度分析（含关键证明）

| 部分 | 复杂度 |
|------|--------|
| `set(nums)` 建集合 | O(n) |
| 外层遍历集合 | O(n) |
| 内层 `while` **总计** | **O(n)** |
| **合计** | **O(n)** |

**为什么内层 `while` 总计只有 O(n)**：内层仅在「起点」处进入，而每条连续段**有且仅有一个起点**，
所以段内每个元素只会被"数到"一次；所有内层迭代加起来 ≤ n。

> 这里用到了两个重要概念：
> 1. **加法法则**：多个 O(n) 步骤顺序执行，总复杂度仍是 O(n)（系数可忽略）；
> 2. **摊销分析**：单个起点的那轮计数可能很长，但均摊到所有元素上，平均每个元素只被访问常数次。

## ⚠️ 本题的两个 O(n²) 陷阱（用户实测发现）

### 陷阱一：遍历「原数组」而不是「集合」

```python
# ❌ 错误写法：遍历原数组
for n in nums:                    # 含重复元素！
    if n - 1 in exists_dict:
        continue
    ...往后数整段...
```

同一段会被**重复计数**：若某起点值出现了 k 次，整段就被完整数 k 遍。

实测（`example2.txt`，n=50000，其中值 0 重复 25000 次）：
- 集合版：只遍历 25001 个唯一值 → 约 5 万次操作 → **2.3 ms**
- 原数组版：25000 个重复起点 × 每次数 25001 个 → **6.25 亿次操作** → **超时**

**修复**：遍历 `set(nums)` 或 `dict.keys()`（等价于去重）。

### 陷阱二：用 list 承载集合

```python
num_set = list(set(nums))         # ❌ 数据是去重的，但容器不支持 O(1) 查找！
```

`in` 操作的成本由**容器类型**决定：

| 容器 | 底层结构 | `x in 容器` |
|------|---------|------------|
| list | 连续数组 | 逐个比较，**O(n)** |
| set | 哈希表 | 哈希定位，**O(1)** |

实测单次查找耗时（ns）：

| 容器规模 | `in set` | `in list` | set 快多少倍 |
|:---:|:---:|:---:|:---:|
| 10 | 18 | 48 | 2.7x |
| 100 | 17 | 310 | 17.7x |
| 1,000 | 23 | 2,571 | 109x |
| 10,000 | 22 | 26,508 | 1,178x |
| 100,000 | 23 | **281,928** | **11,997x** |

算法层面实测（随机数据）：

| n | set 版 | list 版 | list 慢 |
|:---:|:---:|:---:|:---:|
| 500 | 0.044 ms | 2.29 ms | 52x |
| 1,000 | 0.093 ms | 8.79 ms | 94x |
| 2,000 | 0.229 ms | 38.1 ms | 167x |
| 4,000 | 0.380 ms | 149.7 ms | **394x** |

> **O(n²) 的指纹**：n 增长 8 倍（500→4000）时，set 版耗时增长 8.6 倍（线性），
> list 版增长 65 倍（≈ 8² = 64，平方）。

## 容器选型速查（本题的延伸收获）

| 判断标准 | 选择 |
|---------|------|
| 只关心「在 / 不在」、去重、集合运算（交并差） | **set** |
| 需要「键 → 值」映射：下标、计数、分组、记忆化 | **dict** |
| 需要按下标随机访问 / 有序 | list |
| 小规模（几十个）数据 | list 也可以（缓存友好），但上百即必须 set |

**口诀：只问「在不在」→ set；要带「信息」→ dict；要「算术」→ set。**

## 本题考点

| 考点 | 内容 |
|------|------|
| 哈希集合 | 用 O(1) 存在性查询替代排序 |
| 起点判定 | 「`x-1` 不在集合中」等价于「x 是一段连续序列的起点」 |
| 摊销分析 | 内层循环总次数 ≤ n 的证明 |
| 容器选型 | 遍历对象（集合 vs 原数组）、容器类型（set vs list）都直接影响复杂度 |
